# Fase 3 — Alunos e estrutura

Base: `61bf511`, branch `codex/lss-v3-academics-complete`. Especificação v3 com decisões posteriores: experiência normal, dados fictícios locais e API dedicada adiada.

## Integridade e compatibilidade

`academic` acrescenta uma estrutura versionada com instituição, anos, pessoas, matrículas, colocações, rascunhos e eventos ao snapshot v3. Exportações anteriores sem este bloco continuam legíveis. A leitura deriva o modelo sem escrever, sem fundir nomes semelhantes e sem alterar saldos. A primeira operação guarda o modelo e as projecções de uma vez, conservando a origem anterior já preservada na persistência.

A pessoa é permanente. O registo Student existente torna-se a projecção compatível de uma matrícula anual, preservando IDs de pagamentos/cobranças/recibos. O número permanente pode aparecer em duas matrículas da mesma pessoa; outra pessoa não pode receber o mesmo número novo. Números legados ambíguos são assinalados para revisão explícita. O número da pauta é reservado por turma/ano e não volta a ser atribuído depois de uma saída/transferência.

A revisão do repositório recusa prévias de outra aba. A mesma tentativa recupera o resultado e conteúdo diferente com o mesmo ID é recusado. Isto continua a ser uma gravação local consistente, não uma transacção multiutilizador no servidor. Não foi criada base, SQL/ORM, API, credencial real ou backup central.

## Percursos e testes

Testes de domínio cobrem matrícula/rascunho, repetição e resposta recuperada, falha de gravação, última vaga/revisão obsoleta, correspondências/pesquisa, renovação anual com dívida intacta, transferência imediata/futura, números não reutilizados, sala única/conflitos/capacidade, calendário sem assumir Março, ano único activo, correcção de contacto, bolsa integral, desistência/cancelamento com antecipação/crédito e importação com validação das relações.

Testes de UI cobrem os três passos, Guardar e pagar no aluno correcto, recibo, rascunho retomável, correcção/contacto/histórico, retorno/recarregamento da ficha, consulta pelo Director, cadastro único de sala, renovação, transferência, confirmação de fecho, rascunho da inscrição e paginação.

Happy DOM calcula incorrectamente a validade nativa de valores com `step="0.01"` por resto de ponto flutuante. O ensaio de confirmação da inscrição submete o formulário directamente para verificar a validação real da aplicação, persistência e recibo. Isso não declara a validação nativa do navegador/mobile como ensaiada.

## Limites explícitos

- Vagas, autorização e comandos são validados no serviço local. Servidor, disputa simultânea entre postos e critérios P dependem da API adiada.
- Os calendários actuais cobrem um ano civil de quatro algarismos, com meses configuráveis e sem impor Março. Calendários atravessando Dezembro não estão implementados nesta etapa.
- Transferir conserva cobranças já registadas e os pagamentos. Vigências de preços, emissão automática, precisão/multas e ajustamentos de novas regras ficam para a fase 4; não são declarados prontos por esta fase académica.
- O Dialog de inscrição conclui recebimento em numerário com o serviço existente. Conferência, anexos, aplicação/devolução de crédito e impressão completa continuam para a fase 5. Os originais e aplicações libertadas ficam no histórico/ajustamentos.
- A revisão completa de oito larguras, teclado virtual, impressão e utilização real ainda não foi concluída. O preview local disponível acrescenta argumentos Vite incompatíveis com Next.js; não alterar infra-estrutura nem protecções de preview para o contornar.

A conclusão desta branch é de implementação local para revisão; não declara prontidão para piloto/produção com dados reais.
